# Assembly-only HOR comparator: exact engineered control (2026-09-17)

## Frozen scientific scope

This is one **development** control, not held-out evidence and not a biological centromere. The deterministic generator `benchmarks/scripts/build_assembly_hor_comparator_v1.py` creates five 171-bp monomer templates from a common ancestor, with 34 substitutions per template and one further substitution per emitted copy. It places 40 HOR units in a single 34,371-bp array, with four exact length/order variants at HOR indices 7, 18, 29 and 35. The 36,371-bp FASTA includes two 1,000-bp random flanks. Every copy and HOR has a 0-based half-open truth interval in `truth_monomers.tsv` and `truth_hors.tsv`. Truth describes **engineered sequence**, not native centromere copy truth, plant biology, or read evidence. The 100–400-bp monomer-length and five-monomer/40-HOR simulation design was checked against the pinned [HiCAT simulation source](https://github.com/xjtu-omics/HiCAT-human/blob/a6ecf595947b4c4ed10106baa6e7d0fd58ccbd84/simulation/simulateHOR.py); this independent control is not that program's output.

The shared input is `benchmarks/assembly_hor_comparator_v1/control/control.chr1.fasta`, SHA-256 `f2a968383dd9bef0af38ee5891ce97b7228f67cbe71495e36340adc20d956e8e`. `candidate_monomers.fa` is archived as truth but **withheld from both whole-pipeline tools**. The frozen protocol, native command arrays, resource settings and output scoring rules are in `protocol.json` and `run_manifests/`. CENdetectHOR pipeline revision `969f4ef515fadd8b8a035357294971ff57d4618f` with library `bdc3a9df5b60adafdd17eaded1b994edd22aae03`, and TideCluster source `8131547e75f73a1e61298a89ff4e861fbd613b7e` with TideHunter 1.4.3 were used from the existing project-local installations. Both received the same assembly FASTA, one requested CPU and no reads. The native commands can be replayed with `python benchmarks/scripts/profile_stage_resources.py --manifest <one run_manifests JSON> --outdir <fresh output directory> --interval 0.2`, after `prepare_assembly_hor_comparator_v1.py` creates clean ignored workdirs. Runs were sequential on the same macOS host. The two-stage TideCluster wall time is summed, while its peak sampled process-tree RSS is the maximum stage peak. Aggregate RSS may count shared pages more than once. This small control does not estimate performance on full chromosomes.

The TideCluster clustering stage was **not** given `--max_memory`; the 1-GB setting applied only to TideHunter. The 8.2-GiB value is the profiler's sampled *sum of live process-tree RSS*, with possible shared-page double counting, not measured unique physical memory. The sample trace rises during clustering and remains near the peak for several seconds. No scaling conclusion follows from one 36-kb control. The native `control_clustering.gff3`, TideHunter GFF3 and consensus FASTA are archived under `benchmarks/assembly_hor_comparator_v1/native/` with SHA-256 in `score_primary.json`; resource traces and stderr are under `profiles/`. `score_assembly_hor_comparator_v1.py` recomputes the exact interval metrics and rejects changed input hashes or run states.

An initial CENdetectHOR attempt on the same bases used a conventional `>control.chr1` FASTA header and failed in the upstream periodicity script because it parses a coordinate-bearing header. That failed profile is retained under `profiles/cendetecthor/`; the FASTA title alone was changed to `>control:0-36371`, the control SHA-256 was re-frozen, and **both tools** were run on the corrected file. The header fix preceded any structural output.

Two subsequent CENdetectHOR attempts are explicitly **exploratory interface sensitivity checks**, outside the primary frozen setting. At `windowSize=5000` without a monomer-length prior, the periodicity stage nominated a 1,710-bp repeat span, the extracted consensus FASTA was empty, and `Extract5mon.py` raised `NameError` while reading it. At `windowSize=5000` with the truth-derived `expMonSize=171` supplied, the filter generated no `_main.bed`, so Snakemake failed during `cp`. Their frozen command manifests, stderr, resource traces, partial BED/FASTA artifacts and hashes are retained. Neither is a completed accuracy run; the known-length case is additionally ineligible for a no-prior ranking. No further CEN parameter search was done on this control.

## Endpoint interpretation

The primary comparison establishes a common **assembly input** and a TideCluster array-localization result. It does not establish a valid CENdetectHOR-vs-TideCluster accuracy ranking because CENdetectHOR produced no final prediction. TideCluster's 855-bp period supports detection of the canonical **repeat length** on this engineered array; it does not demonstrate 171-bp monomer decomposition, five-family clustering, correct HOR label order, or recovery of the four engineered variants. The two-stage TideCluster run does not include its later TAREAN/KITE HOR analysis. TandemX M2 currently uses supplied candidate monomers and, where applicable, reads; scoring that against no-prior whole-pipeline tools would leak truth or change the endpoint. TandemX is therefore N/A here. The assembly–read discordance experiment belongs to a separate read-supported benchmark, where an assembly-only annotation tool must not be scored as a false negative for a task it cannot perform.

Focused independent generator check: `conda run -n tandemx-dev python -m pytest tests/unit/test_assembly_hor_comparator_v1.py -q` → `1 passed`. The test verifies every truth copy's sequence, one-substitution relationship to its template, contiguous coordinates, four variant paths and source digest. It does not validate competitor accuracy beyond the scored native files.
