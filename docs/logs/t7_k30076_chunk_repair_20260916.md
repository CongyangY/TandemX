# K30076 corrupted chunk repair, 2026-09-16

Scope: one previously confirmed invalid `SRR33996329` spot range,
4,615,107--4,640,106 (25,000 spots). The frozen benchmark selection,
converter and target denominator were not changed. Large T7 analysis was not
resumed before this repair.

## Pre-repair identity

The attempt-001 `spot_4615107_4640106.fastq.gz` on T7 still had 370,177,772
bytes and SHA-256
`06bdc011167b5ddbf301da9fca458a79a4264a2ec86b74194cf6fe653cce4e56`,
matching the earlier repeatable corruption observation. Its successful
historical receipt required SHA-256
`2e3fb14389a5674ec1a62c32db13e0476e5aa62aa1c8501bd86968af10734867`.
The attempt-002 20-byte and attempt-003 306,462,727-byte `.partial` payloads
were failed, unpublished outputs. Their failure receipts and stderr were
retained.

## Direct source recovery and promotion

A one-spot direct, no-proxy `vdb-dump` probe returned exit 0, 72,070 stdout
bytes and no stderr. The bounded 25,000-spot command then streamed directly to
internal storage through the existing strict converter in 539.434 seconds.
The independently reaudited replacement has 25,000 continuous IDs,
440,057,073 bases, 370,177,772 gzip bytes and SHA-256
`2e3fb14389a5674ec1a62c32db13e0476e5aa62aa1c8501bd86968af10734867`.
Its raw tab-stream SHA-256
`6f6112e161f597c7697ccf3c3dadd452fc35d836f0df2a39057067ff195371f2`
also matches the original successful receipt. Thus this re-extraction restored
the expected bytes, not merely a plausible same-length FASTQ.

The internal backup and full extraction receipt are under
`tmp/k30076_chunk_recovery_20260916/` and are deliberately not versioned as
source files. A 1 MiB and then 64 MiB isolated T7 write/fsync/readback/delete
probe both matched SHA-256. The verified replacement was copied to a **new**
T7 directory,
`/Volumes/T7/Codex/TandemX/data/subsets/peanut_k30076_vdb_spot_range_benchmark_20260912/block_02_chunk3_repair_20260916/chunks/`,
with a staged file, fsync, full SHA-256 readback and a second readback after
publication. `promotion_receipt.json` on the internal disk records paths and
hashes. The original failed attempt directory was not silently overwritten.

Only after both the internal backup and new T7 copy matched the expected hash
were the three exact invalid payloads removed. The cleanup code first checked
each path, length and old hash; `cleanup_receipt.json` records the removed
lengths and hashes. The original attempt-001 receipt and aggregate, and the
attempt-002/003 failure logs, remain as historical evidence. They must not be
read as a currently valid attempt-001 aggregate, because its referenced chunk
path is now absent.

## Volume and remaining validation boundary

`diskutil verifyVolume /Volumes/T7` could not unmount exFAT `disk5s2` because
`mds` dissented; other running projects also held T7 working directories.
`fsck_exfat -n -x /dev/rdisk5s2` returned permission denied even when run via
an escalated command. A short filtered macOS log window showed no new EIO or
USB disconnect, which does not rule out recurrence. `system_profiler` showed
the T7 behind a VIA Labs USB device at **Up to 480 Mb/s**; there is no prior
link-speed measurement establishing when or why it negotiated USB 2.0.
Successful bounded file readbacks establish those bytes at this point in time,
not whole-volume or physical connection health.

All 34 selected block-2 chunks were then independently rechecked: each file
matched its receipt SHA-256 and byte count, decompressed fully, had valid
FASTQ records, continuous absolute spot IDs, and matching record/base totals.
The 33 unchanged attempt-001 chunks and the new repaired third chunk total
**845,098 records and 15,027,572,584 bp** (10.1181243578x against the frozen
1,485,213,272-bp assembly span). The new block aggregate is
`/Volumes/T7/Codex/TandemX/data/subsets/peanut_k30076_vdb_spot_range_benchmark_20260912/block_02_chunk3_repair_20260916/block_receipt_repaired.json`,
SHA-256 `b7be4a337c1062278e6f9dc4fc0a3e1b0e8c8f276429f7be340f5273c18d0097`.
It references the selected paths and receipts and was itself fsynced and
read back from T7. The historical attempt-001 aggregate remains invalid.
Block 1 still needs post-disconnect readback, block 3 is unstarted, and the
common 30x comparator remains ineligible.

Compact durable evidence is in `docs/evidence/t7_k30076_repair_20260916/`:
the re-extraction receipt, promotion/cleanup receipts, complete 34-row
revalidation, and repaired block aggregate. The 370-MB FASTQ and complete
internal backup are deliberately outside Git.

## Separate confirmed generated-output damage

The V14167 interrupted `formal_run_v1_execute/normalization.sqlite` was
99,483,648 bytes with SHA-256
`a2739fcd689ce15e4a1203ddac1901796105824f9a748bbd9d3de06cf8fce58e`.
Read-only `PRAGMA quick_check` raised `DatabaseError: database disk image is
malformed`; `lsof` found no process using this file. After recording its exact
identity and error, only that malformed SQLite output was removed. A distinct
older `formal_run_v1/normalization.sqlite` returned `ok` on `quick_check`, but
was **not** substituted because it is a different interrupted attempt. The
formal three-tool comparison remains incomplete and needs valid native
comparator inputs before its normalization can be regenerated.

The restoration tool is `benchmarks/scripts/promote_recovered_fastq.py`; its
focused tests cover successful promotion and refusal of damaged bytes or an
incomplete receipt, plus cleanup after an injected target `ENOSPC`. Four
focused tests passed. The full repository suite passed 958 tests before the
last `ENOSPC` test was added; the final focused rerun passed all four. No
production TandemX estimator changed.
